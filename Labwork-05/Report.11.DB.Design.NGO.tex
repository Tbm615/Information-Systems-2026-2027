\section{The problem}
An NGO needs a single database covering all of its projects. The organization runs head offices in several countries, and every head office coordinates the projects carried out in its own country. Each head office is described by an identifier, its city and country, its address, a phone number and the director's name. A head office is responsible for a number of projects; a project has a code, a title, start and end dates, an allocated budget and the name of the person in charge. Every project consists of actions, and a single action may concern several cities. A city is recorded with an identifier, its name, its country and its population. Finally, the database must show which actions take place in which city, with a short description of each action, as well as the share of the project's investment assigned to that city.

\section{How I made the structure}

\subsection{Conceptual model}
The requirements lead to four entities: head office, project, action and city.
\begin{itemize}
    \item \textbf{Head\_office}: office id (key), city, country, address, phone, director name.
    \item \textbf{Project}: project code (key), title, start date, end date, budget, person in charge.
    \item \textbf{Action}: action id (key) and a description.
    \item \textbf{City}: city id (key), name, country, population.
\end{itemize}

Relationships:
\begin{itemize}
    \item Each head office is in charge of many projects, while each project is managed by exactly one head office (one to many).
    \item Each project contains many actions, while each action is part of exactly one project (one to many).
    \item A project may invest in several cities, and a city may receive investment from several projects (many to many). The investment amount is an attribute of this relationship.
    \item An action may involve several cities, and a city may host several actions (many to many).
\end{itemize}

\subsection{Logical model}
\begin{itemize}
    \item \texttt{Head\_office(\underline{OfficeID}, City, Country, Address, Phone, DirectorName)} -- primary key: \texttt{OfficeID}
    \item \texttt{Project(\underline{ProjectCode}, Title, StartDate, EndDate, Budget, PersonInCharge, OfficeID)} -- primary key: \texttt{ProjectCode}; foreign key: \texttt{OfficeID} $\rightarrow$ \texttt{Head\_office}
    \item \texttt{Action(\underline{ActionID}, Description, ProjectCode)} -- primary key: \texttt{ActionID}; foreign key: \texttt{ProjectCode} $\rightarrow$ \texttt{Project}
    \item \texttt{City(\underline{CityID}, CityName, Country, Population)} -- primary key: \texttt{CityID}
    \item \texttt{Project\_city(\underline{ProjectCode, CityID}, Investment)} -- primary key: \texttt{(ProjectCode, CityID)}; foreign keys: \texttt{ProjectCode} $\rightarrow$ \texttt{Project}, \texttt{CityID} $\rightarrow$ \texttt{City}
    \item \texttt{Action\_city(\underline{ActionID, CityID})} -- primary key: \texttt{(ActionID, CityID)}; foreign keys: \texttt{ActionID} $\rightarrow$ \texttt{Action}, \texttt{CityID} $\rightarrow$ \texttt{City}
\end{itemize}

Each of the two many to many relationships is mapped to its own table, \texttt{Project\_city} and \texttt{Action\_city}. The investment column is placed in \texttt{Project\_city}, since its value is determined by the project and the city together.

Normalization: every attribute holds an atomic value (1NF). In the two tables with composite keys, each non-key column depends on the full key rather than on part of it (2NF), and no non-key column depends on another non-key column (3NF).

\subsection{Physical model}
The ER diagram can be found in \texttt{Labwork-05b.png}. The identifiers of offices, actions and cities are generated with \texttt{AUTO\_INCREMENT}. Budget and investment are declared as \texttt{DECIMAL(15,2)} so that monetary amounts are stored exactly. All foreign keys are defined with \texttt{ON UPDATE CASCADE} and \texttt{ON DELETE CASCADE}.

\section{SQL commands to create the database}
\begin{Verbatim}
DROP DATABASE IF EXISTS ngo_db;
CREATE DATABASE ngo_db;
USE ngo_db;

-- 1. Table: Head_office
CREATE TABLE HEAD_OFFICE (
    OfficeID INT NOT NULL AUTO_INCREMENT,
    City VARCHAR(100) NOT NULL,
    Country VARCHAR(100) NOT NULL,
    Address VARCHAR(255) NOT NULL,
    Phone VARCHAR(50) NOT NULL,
    DirectorName VARCHAR(100) NOT NULL,
    PRIMARY KEY (OfficeID)
);

-- 2. Table: Project
CREATE TABLE PROJECT (
    ProjectCode VARCHAR(50) NOT NULL,
    Title VARCHAR(255) NOT NULL,
    StartDate DATE NOT NULL,
    EndDate DATE NOT NULL,
    Budget DECIMAL(15, 2) NOT NULL,
    PersonInCharge VARCHAR(100) NOT NULL,
    OfficeID INT NOT NULL,
    PRIMARY KEY (ProjectCode),
    FOREIGN KEY (OfficeID) REFERENCES HEAD_OFFICE(OfficeID)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);

-- 3. Table: Action
CREATE TABLE ACTION (
    ActionID INT NOT NULL AUTO_INCREMENT,
    Description TEXT NOT NULL,
    ProjectCode VARCHAR(50) NOT NULL,
    PRIMARY KEY (ActionID),
    FOREIGN KEY (ProjectCode) REFERENCES PROJECT(ProjectCode)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);

-- 4. Table: City
CREATE TABLE CITY (
    CityID INT NOT NULL AUTO_INCREMENT,
    CityName VARCHAR(100) NOT NULL,
    Country VARCHAR(100) NOT NULL,
    Population INT NOT NULL,
    PRIMARY KEY (CityID)
);

-- 5. Table: Project_city
CREATE TABLE PROJECT_CITY (
    ProjectCode VARCHAR(50) NOT NULL,
    CityID INT NOT NULL,
    Investment DECIMAL(15, 2) NOT NULL,
    PRIMARY KEY (ProjectCode, CityID),
    FOREIGN KEY (ProjectCode) REFERENCES PROJECT(ProjectCode)
        ON UPDATE CASCADE
        ON DELETE CASCADE,
    FOREIGN KEY (CityID) REFERENCES CITY(CityID)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);

-- 6. Table: Action_city
CREATE TABLE ACTION_CITY (
    ActionID INT NOT NULL,
    CityID INT NOT NULL,
    PRIMARY KEY (ActionID, CityID),
    FOREIGN KEY (ActionID) REFERENCES ACTION(ActionID)
        ON UPDATE CASCADE
        ON DELETE CASCADE,
    FOREIGN KEY (CityID) REFERENCES CITY(CityID)
        ON UPDATE CASCADE
        ON DELETE CASCADE
);
\end{Verbatim}
